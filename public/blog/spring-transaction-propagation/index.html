Spring @Transactional Propagation: What to Use and When

What happens when one Spring service calls another? Here is how the propagation options handle that, and the cases where each one is useful.

By Mohd Azim · 4 November 2026 · 4 min read

When one Spring service calls another, the second method has to decide what to do with the transaction already in progress. That decision is propagation. It applies to transactions managed inside your application; it cannot make a database update and a remote HTTP call commit or roll back together.

REQUIRED — the usual choice

If a transaction is already open, REQUIRED joins it. If not, Spring starts one. This is the default, and it fits most business operations. For example, saving an order and its items should normally succeed or fail together.

Because both methods share the same transaction, an inner method can mark it rollback-only. Catching an exception in the caller does not necessarily make that transaction safe to commit.

REQUIRES_NEW — commit separately

This pauses the current transaction and starts another one. The inner work can commit even if the outer transaction later rolls back. That can be useful for an audit record that must survive a failed business operation.

Use it sparingly. The outer transaction may still hold locks or a database connection while it is paused, and the new transaction needs its own resources. It is not a general fix for rollback problems.

SUPPORTS — join if there is a transaction

SUPPORTS joins a transaction when the caller has one; otherwise, the method runs without one. It can suit work that is fine either way, but it does not guarantee atomic writes when called on its own.

NOT_SUPPORTED — run outside the caller's transaction

This suspends any current transaction while the method runs. It can be useful for work that should not keep a database transaction open, such as an independent operation that takes a while. It is a poor fit when the work needs the caller's transactional view or must roll back with it.

MANDATORY — require a transaction

MANDATORY joins the caller's transaction and throws an IllegalTransactionStateException if there isn't one. Use it when a lower-level operation must always be part of a larger transactional workflow. It makes accidental calls outside that workflow fail early.

NEVER — reject a transaction

NEVER runs without a transaction and throws an IllegalTransactionStateException if one is active. This is uncommon; choose it only when running inside a transaction is specifically an error, not as a routine performance setting.

NESTED — use a savepoint

When a transaction exists, NESTED creates a savepoint. The inner work can roll back to that point while the outer transaction continues. Without an existing transaction, it behaves like REQUIRED. It is not the same as REQUIRES_NEW: the nested work does not commit independently, and savepoint support depends on the transaction manager.

A few things to check

  • REQUIRED is a good starting point. Pick another option when you need its particular commit or rollback behavior.
  • With Spring's default proxy-based transactions, a method calling another transactional method on the same object bypasses the proxy. The second method's propagation setting is then not applied.
  • By default, Spring rolls back on unchecked exceptions and Error, but not every checked exception. Use rollbackFor when checked exceptions should trigger a rollback.
  • A database transaction cannot undo a request already sent to another service. For cross-service workflows, consider an outbox or a saga rather than keeping a database transaction open across network calls.

In most cases, REQUIRED is enough. I reach for another propagation mode only when its boundary and failure behavior are clear.
